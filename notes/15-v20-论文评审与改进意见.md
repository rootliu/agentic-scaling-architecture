# 论文评审：《A Contract-Centered Architecture for Scalable and Manageable Agentic Runtimes》(v20)

- **作者**：Yaxiao Liu
- **类型**：工作预印本（position / architecture paper，非系统实现，无实验数据）
- **页数**：27 页；参考文献 14 篇（多为 2026 年 arXiv 预印本）
- **核心模型**：运行时核心 A = ⟨S, H, X⟩，数据底座在栈外；中心科学主张 = 可证伪的“可测试可分离性猜想 (P1)”

---

## 一、内容总结

**问题定位**：企业 AI 部署本质是一个跨组织单元的协调问题（业务、应用/AI、测试、平台、基础设施、安全、运维、数据治理）。单点 use-case benchmark 能证明"一个 agent 完成一个任务"，但无法定义"能力、模型、运行时机制、物理容量、企业数据应该由谁拥有、如何变更、如何准入、如何举证"共同演进。

**四个责任对象（共享组织契约）**：
- **Skill (S)**：可复用、版本化的业务能力资产。`s = ⟨g, i, o, p, e, v⟩`
- **Harness (H)**：运行时编译器与治理者。`(q, u, S) → (D, C, b, τ)`
- **Scaffold (X)**：执行/控制边界与 NFR 所有者。`x = ⟨r, z, l, a⟩`
- **数据底座**：栈外、CIO 独立治理的语义与遥测基础设施（非第四层）

**中心科学主张（P1，可测试可分离性猜想）**：在声明的运行区 Ω 内，若以下六条件通过各自预注册的机制级验收（typed closure、complete mediation、effect non-interference、shared-state isolation、resource invariance、scheduler independence），则 Skill 能力数量与兼容 Scaffold 容量的干预可独立变化。

**方法论亮点**：确定性门禁 + trace 身份使违规可观测/可审计/可归因；业务证据与系统/运行时证据分离；第 9 节给出 9.1–9.8+ 系列证伪协议（含 estimand、预注册边际、证伪标准）；用 Skillware-138K 语料实证"当前 Skill 普遍缺乏 operation closure"，从而论证 Harness 必须强制闭包而非假设。

**配套机制**：选择性激活、上下文分区（前缀缓存）、推导闭包编排、外部数据契约、局部性感知绑定、规划期 dry-run、Intermediate Relation、train-freeze-monitor 的 Skill 生命周期、双子目标奖励。

---

## 二、优点（值得保留）

1. **诚实且成熟的研究姿态**：全文反复区分"能力证据 vs 容量证据"、"设计假设 vs 已证结论"，主动声明 0–100,000 是设计目标而非证据，并单列"Limitations and Threats to Validity"。这在 agent 架构类论文里很少见，是真正的学术严谨。
2. **以 Conway 定律为锚，落地到责任/变更节奏**：Table 1 把"谁拥有、变更多快、稳定契约是什么"讲清楚，是本文区别于大多数"架构图"论文的核心价值。
3. **第 9 节的证伪协议设计扎实**：预注册机制检查、因子实验、边际设定、证伪条件都具体，是可执行的研究纲领。
4. **用真实语料给主张设上下界**：引用 Skillware-138K 说明"元数据信封是主流惯例，但可证伪的 typed 接口在语料层面不可见"，从而论证 Harness 准入的必要性——这是少见的、用证据约束自己声称的做法。
5. **识别了控制面集中风险与降级模式**：承认 Harness 单点故障、fail-closed、缓存新鲜度等，表明作者考虑过生产落地。

## 三、改进意见（按优先级）

### P0 — 影响论文是否成立 / 能否发表

**1. "中心科学贡献"被高估，且 P1 在逻辑上偏弱**
- 问题：P1 的预测是**以六条件通过预注册检查为前提**的；而六条件本身基本就是本架构想强加的设计目标。文中自己也写"passing all six condition checks does not establish separability""系统可用模型外机制补偿某一弱点"。结果 P1 实质上接近"若强隔离成立，则隔离成立"——有循环/定义化风险。
- 真正可证伪、有价值的命题是：**在有用 Ω 内满足六条件的成本/可行性**（而非其逻辑后果）。建议把 P1 重新表述为"成本/可行性猜想"，或明确写清：P1 的有意义部分不是逻辑推导，而是"真实 agent 系统能否以可接受开销满足六条件"。
- 同时建议把"中心科学贡献"重新定位为：**责任分离契约 + 预注册证伪方法论**（P1 只是其一个应用），而非把 P1 单独抬到中心。

**2. 完全缺乏任何实证，且反复"免责声明"反而削弱贡献感**
- 全文每节都加"is a design hypothesis, not proven""design target, not evidence"。诚实但读起来像在不断自我撤销贡献。
- 建议二选一：(a) 至少跑通一个小规模协议（如 9.4 控制面泄漏、或 9.1 选择性激活的规模对比）证明方法论可落地；或 (b) 明确把文章重新定位为"manifesto / research program"，把各章贡献表述为"待验证的设计原则"而非"contributions"。当前介于两者之间，容易被 reviewer 判为"空架构"。

**3. "effect non-interference / scheduler independence"应落地到既有学术谱系**
- 这两个概念本质就是安全/指称语义里 40 年历史的 **non-interference**（Goguen & Meseguer 1982）与信息流格。文中完全没引用，像是重新发明。
- 同样，"complete mediation"是经典 capability security（Miller et al.），"Harness 治理循环"近似 MAPE-K 环，NFR 列表近似 ISO/IEC 25010。
- 建议：补一节"Foundations"，把六条件一一映射到既有形式化/系统工程文献。这既强化 novelty boundary，也显示架构站在巨人的肩上，而非只引用 2026 预印本。这是性价比最高的引用补充。

### P1 — 影响严谨性与可读性

**4. "contract"一词三重过载，建议明确拆分**
- 既有"组织责任契约"（Conway 式社会承诺），又有"Harness contract"（技术产物 C），还有"数据 contract"。
- 建议：用不同词区分，例如"responsibility contract（社会）"vs"machine contract / resolved contract（技术）"。

**5. 数据底座与 Intermediate Relation 欠定义**
- 数据底座是"栈外 CIO 治理的语义与遥测基础设施"，但"语义 join 怎么实现、数据模型是什么、Intermediate Relation 的 schema 长什么样"全文未形式化（abstract 提到 reconstructive reflection / Intermediate Relation，正文基本没展开）。
- 建议：给一个具体的 Intermediate Relation schema 示例 + 一个 join 查询的端到端例子。否则这部分像口号。

**6. 缺少与具体现有系统的对比**
- 正文 related work 只讨论 4–5 篇；对 LangGraph / AutoGen / CrewAI / Bedrock AgentCore / AgentOps 等没有按"能力-容量可分离性"维度做对比表。
- 建议：加一张对比表（维度：准入语义、路径级不变量、容量与能力解耦、审计 replay），明确本文相对现有运行时的增量。

**7. 0–100,000 规模数字出现次数过多，显得"未兑现的雄心"**
- 反复声明"是设计目标非证据"很好，但数字出现太频，读感像在刷存在感。
- 建议：正文只在摘要和一处设计目标声明，其余交给第 9 节的剂量-反应度量；或补一个基于排队论的粗略容量模型，说明在该责任拆分下为何"可能"达到而非纯口号。

### P2 — 润色与完整性

**8. 冗余偏高，建议压 15–20%**
- "probabilistically written, deterministically executed""separate evidence planes""design target not evidence"等短语跨 27 页反复出现。建议把诚实性免责收敛到一个"Scope & Claims"框，章节内不再重复。

**9. 双子目标奖励 (P15) 与 Intermediate Relation 论证不足**
- 这两点在 abstract 被列为贡献，但正文（尤其 8.5）展开得薄。建议要么扩写，要么降级为 future work，避免"标题党"。

**10. 缺失的治理失败模式**
- Limitations 自承"human approvals / multi-tenant incentives / cross-org trust 可能代表性不足"。建议补一小节"dispute & escalation 协议"：当两个业务单元争夺某 Skill 所有权、或数据底座不可用时，契约如何裁决/降级——这恰是"组织即契约"主张的试金石。

**11. 形式化偏轻**
- 模型 A=⟨S,H,X⟩ 与签名式之外没有真正的状态转移代数。建议加一小节定义状态转移（或明确声明这是记法而非形式模型），避免读者期待代数而落空。

**12. 长难句可读性**
- 摘要与数处长句嵌套过深（如数据底座那句）。学术风格可接受，但可拆分以提升可引述性。

## 四、优先行动建议（如果你要推进到可投稿状态）

1. **重定位贡献叙事**：把"责任分离契约 + 预注册证伪方法论"作为中心贡献；P1 作为应用示例并补"成本/可行性"维度。
2. **跑一个最小实验**（9.1 或 9.4 的小规模版）让方法论从"宣称"变"示范"。
3. **补 Foundations 引用**（non-interference 1982、capability security、MAPE-K、ISO 25010）——低成本高收益。
4. **形式化数据底座 / Intermediate Relation**，给一个可复现的 join 例子。
5. **加现有系统对比表 + 排队论容量模型**。
6. **压冗余、拆 contract 语义、补 dispute 协议**。

整体判断：这是一篇**视野成熟、方法论诚实、但尚停留在"架构主张"阶段**的论文。架构分层本身有真实价值，最大的短板是"声称可证伪却尚无任何证伪执行"与"六条件偏定义化"。把贡献叙事与实证缺口处理到位后，具备投 architecture/management 类 venue 的潜力。

## 五、v22 修订复核（2026-08-04）

> 上述 12 条意见是对 v20 的历史评审，不回写。当前 v22 为 16 页、8 图的聚焦修订。

### 已实质改善

1. **贡献叙事已收敛**：中心不再是泛化的“三层架构”，而是 contract-centered runtime 及其可管理性研究；Skill、Harness、Scaffold 分别拥有版本化行为、准入/逻辑控制、物理执行/隔离。
2. **P1 的适用边界更明确**：主张限定在 operating region `Ω` 内，并改成 bounded separability 的可证伪读取；六项条件均作为可测义务报告。
3. **契约不再只是抽象名词**：Figure 2 明确 `I/O, G, A, B, V` 五组字段，其中 `A` 同时覆盖 authority、effects 与 evidence duties，`V` 固定所有影响复现的版本。
4. **实验判决更克制**：采用 cluster-period randomized crossover，并把结果限定为 `supported / falsified / inconclusive`；功效不足不能支持可分离性。
5. **篇幅和图表更聚焦**：从 v21 的 33 页压缩为 16 页，以 8 张图串联责任、契约、数据、执行与验证，降低重复免责声明造成的“自我撤销”感。
6. **完整序列排除偏差已显式处理**：按进入/退出处理、周期和顺序报告 reset failure，并以 assignment-based ITT 边界和 tipping-point 分析检查 complete-sequence 主估计；失败不平衡或判决不稳健时归为 `inconclusive`。

### 仍未解决的核心风险

1. **尚无本文实测结果**：v22 仍是 architecture/research-program paper。六项义务是否可完整工具化、满足它们的成本以及跨环境外部效度，都必须由后续最小可行研究回答。
2. **`supported` 不是“证明独立”**：它只表示在预登记 `Ω`、margin、功效与仪器条件内未触发证伪标准；任何更强外推都不成立。
3. **经典学术谱系仍受日期规则约束**：non-interference、complete mediation、MAPE-K 与 NFR 的历史来源是否作为 foundations 例外纳入，仍需在投稿前做明确编辑决策。
4. **组织与治理实证仍薄弱**：四类责任对象的 owner 划分、争议升级和跨企业可迁移性尚未经过组织研究验证。

### 投稿前最近一步

优先执行一个可审计的最小实验：固定模型、policy 与 workload family，在两个 Scaffold class 上运行集群周期随机交叉设计，公开六项义务率、语义不变性区间、容量响应、交互估计、achieved power 及关闭违规通道的成本。无论得到 `supported`、`falsified` 还是 `inconclusive`，都比继续扩写架构说明更能提高论文可信度。
