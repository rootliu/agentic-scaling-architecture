# v20 企业 AI 运行时架构：中文综合

> **定位**：本文是 v20 论文重构的中文架构锚点。它综合企业部署动机、四类责任对象、稳定契约、语义连接、非功能需求与双评估平面；不把尚未完成的实现或实验写成已有结果。

## 1. 问题：企业需要共同部署契约，而不只是单点 use case

企业 AI 通常沿既有组织边界组装：业务部门定义目标，应用与自动化团队实现能力，AI 平台治理模型和 agent，云与服务器平台提供容量，SRE、运维和安全维持生产属性，CIO 或企业数据权威治理语义与数据。模型、agent、框架、企业系统和数据的变化速度不同，若没有明确交接契约，各团队只能围绕单个 use case 临时集成。

业务基准可以回答“一个 agent 是否完成一个任务”，但不能单独回答能力如何被准入、组合、授权、绑定到容量、追踪和审计。v20 因而把架构表述为一组可共享、可测量的组织契约，而非一种强制组织图。

Conway（1968）仅作为历史背景：系统结构会反映设计组织的沟通结构。本文进一步提出一个**收窄后的自有命题**：

> 对企业 AI 而言，IT 架构可以成为业务与技术团队之间的共同组织契约，使沟通、所有权、变化节奏和证据义务显式化。

“企业 IT 架构就是企业沟通协议”不是外部作者的原话或结论，也不得以引语形式归因给 Conway 或其他作者。

## 2. 四类责任对象

### 2.1 Skill：可复用、版本化的业务能力与流程资产

Skill 描述一个有边界的企业任务，至少包含目标、适用条件、类型化输入/输出、允许的 effects、测试、证据要求和已验证版本。它拥有业务语义，但不拥有运行时准入、物理执行或企业数据治理。

### 2.2 Harness：运行时编译器与治理器

Harness 位于业务能力与物理执行之间，把当前被激活的 Skill 编译为可执行、可治理的路径。它负责选择性激活上下文与 Skill，组合工具、数据和多模态能力，构造类型化图，执行路径级授权、预算、策略、证据与 release gates，协调多 agent / 多进程，捕获 trace、replay 与 provenance，并把已准入工作绑定到兼容的 Scaffold 容量。

Harness 拥有运行时治理，但不拥有业务含义、物理资源或企业数据本体。

### 2.3 Scaffold：执行与控制边界及 NFR 负责人

Scaffold 由平台、云/服务器场、SRE、安全和运维能力构成，提供资源、调度、隔离、locality、identity、attestation 与执行原语。它暴露可强制执行的事实和边界，但不解释 Skill 的业务语义，也不替 Harness 决定当前应激活哪条能力路径。

### 2.4 数据基盘：栈外、由 CIO 独立治理的语义与遥测基础设施

数据基盘不是第四个运行时层，而是技术栈外的独立基础设施。它由 CIO 或同等企业数据权威与领域 data stewards 治理，负责跨系统的语义连接、受治理访问与 policy-aware routing、provenance / lineage、模型-agent-Harness-业务遥测集成，以及源 registry 与输出 registry 之间的版本化中间表示。

数据基盘拥有企业数据语义和路由契约，但不调度 agent，也不拥有运行时容量。

## 3. 所有权、变化节奏与稳定契约

| 对象 | 主要企业 owner | 典型变化节奏 | 稳定契约 |
|---|---|---|---|
| Skill | 业务产品 owner + AI/自动化开发者 | 小时到周 | 目标、类型化 I/O、effects、测试、证据、版本 |
| Harness | AI 平台/运行时/治理团队 | 天到月 | 准入、激活路径、effects、绑定约束、后置条件、trace |
| Scaffold | 平台、云/服务器场、SRE、安全、运维 | 周到年 | 资源、隔离、locality、identity、attestation、执行 |
| 数据基盘 | CIO/数据权威 + 领域 data stewards | 周到年 | 语义访问、provenance、routing、lifecycle、中间表示 |

这是责任和决策权模型，不要求四个对象必须由四个组织实现。一个团队可以实现多个对象，但各对象的稳定契约、证据责任与否决权仍须可区分。

## 4. 从 Skill 到执行与证据的交接

一次运行的最小交接链为：

1. 业务 owner 发布版本化 Skill，并声明目标、I/O、effects、测试与证据。
2. Harness 只激活当前请求需要的能力，构造类型化路径并完成准入、授权和约束编译。
3. Harness 经数据基盘做 semantic join（语义连接），只注入与当前意图相关的受治理语义、provenance 和 routing facts；源数据增长不应等于全量 schema 进入 context。
4. Harness 根据资源、隔离、locality、identity 与 attestation 约束，把工作绑定到 Scaffold。
5. Scaffold 执行并返回可强制验证的运行事实；Harness 汇总 trace、policy decision、postcondition、replay 与 provenance。
6. 业务/use case 证据和系统/运行时证据分别归档，不以一类证据替代另一类。

数据基盘中的 off-policy 索引、语义总结、遥测聚合和 lifecycle 维护可独立于在线主请求演进。在线路径消费其版本化产物，而不是把整个数据治理 loop 塞进单次 agent context。

## 5. Skill-as-Code：企业资产策略及边界

Skill-as-Code 把反复出现的业务知识与流程沉淀为可版本化、可测试、可审查和可回滚的资产。其预期收益包括：

- 稳定知识不必在每次推理中重新生成，减少 transient context 的污染与幻觉放大；
- 类型化 I/O、effects 和测试使 Harness 能进行准入、组合、追踪与 release gate；
- 版本、验证证据和 rollback 为模型版本变化提供可审计的稳定锚；
- 选择性激活使能力库增长不必线性扩大单次 context。

这些是机制性设计理由，不等于已证明的经验结果。Skill-as-Code 本身不会把概率行为变成完全确定的行为，不保证多个 Skill 的组合安全，不保证描述与真实行为一致，也不证明业务价值、可移植性或逻辑/物理扩展可分离。路径级授权、回归测试、独立 evaluator 和实证协议仍是必要条件。

## 6. Scaffold 的 NFR 与规模目标

Scaffold 对性能、可靠性、可用性、可管理性、可观测性、安全、隔离、跨平台/模型 provider/模型版本的 portability，以及容量演进负责。论文中的“**0 到 100,000 个 admitted/active agents**”只能写成待测设计目标，不是已有实现、基准结果或容量承诺。

该目标至少必须通过以下指标报告：

| 维度 | 必报指标 |
|---|---|
| 准入与容量 | admission throughput、active-agent capacity、queueing delay、saturation |
| 时延与稳定性 | p50/p95/p99 latency、failure rate、retry rate |
| 安全与控制面 | isolation violations、control-plane availability |
| 经济性与外部依赖 | cost per completed run、external-service backpressure |

规模实验还须声明 workload、Skill 分布、模型与工具依赖、并发定义、失败策略和观测窗口。否则“100,000”没有可比较的经验含义。

## 7. 两个不可互换的评估平面

| 评估平面 | 核心问题 | 代表性 measures | 主要证据 owner |
|---|---|---|---|
| 业务/use case | Skill 是否改善预期工作？ | task success、需求全满足率、质量、cycle time、human correction、业务风险、unit economics | 业务 owner + 独立 evaluator |
| 系统/运行时 | 能力能否在企业规模下被可预测地准入和运营？ | contract validity、policy decisions、semantic invariance、throughput、tail latency、availability、isolation、replay、provenance、cost | Harness、Scaffold、安全、SRE、审计 |

强业务/use case 结果不证明可部署性、隔离或规模属性；强系统/运行时结果也不证明业务价值。若系统允许 self-correction，应分开报告 first-attempt grading 与 correction 后结果，避免把恢复能力混写成首次成功率。

### 8.3 历史例外与不合格来源

## 9. 明示限制与未证主张

以下内容仍是架构建议、机制假设或待验证命题：

- 四对象的 owner 分配尚未通过跨企业组织研究验证；
- Harness 的契约是否足以在声明 operating region 内实现逻辑能力增长与物理容量增长的可分离，仍须按既定协议证伪；
- 语义连接能否在异构企业数据上同时保持 coverage、precision、时效性与授权边界，尚无本文实验；
- Skill-as-Code 是否降低模型漂移、context 成本或故障率，必须由对照实验量化；
- `0 到 100,000` admitted/active agents 的容量、尾延迟、隔离和成本目标尚未实现或验证；
- 跨平台、模型 provider 与模型版本的 portability 仍是 Scaffold NFR，不是已证明属性；
- 本文架构不是对现有产品“缺少某能力”的完整性评分，也不推断未公开实现。

因此，v20 的科学核心仍是有边界、可证伪的 Testable Separability Conjecture，而不是普遍独立性、安全性、规模能力或业务价值声明。

### 9.1 P1 六路合取的部分满足读取规则

P1 的判定规则是六个条件（typed closure、complete mediation、effect non-interference、shared-state isolation、resource invariance、scheduler independence）的**合取**。合取本身既是保险也是代价，因此 §5.3 补了一条读取规则：

1. 每个条件工具化为一个**违规率**，而不是一个布尔判断——依次为：每条 activated path 上的 undeclared operations、每次 invocation 的 unbound invocations、每对 path 的 undeclared information-flow edges、每次 mutable access 的 undeclared cross-partition accesses、跨兼容 arm 语义输入字段哈希不一致的字段数、declared fields 之外的 scheduler-labelled flows。预登记的 pass/fail 阈值是该率上的一个声明切点。
2. **全部条件率均 ≤ 阈值**时，P1 按原判定规则读取。
3. **任一率超阈值**时，研究报告 **conditional-engineering result**，而**不给出 P1 判决**——不得把"六个条件里满足了五个"读成"P1 基本成立"。

这条规则在 §11 被如实登记为限制而非仅仅是保险：若合取代价高到 P1 只能在缩减设定下可测，其外部效度本身即成问题。该规则以**追加**方式写入，六条件与既有 rejection criterion 的原文未动（它们属于 spec 的 Scientific Core to Preserve）。

`conditional-engineering result` 是本文自创术语，2026-08-04 修订补上了定义句：**outcome estimand 的完整报告 + 超阈条件具名 + 各自观测值，两个方向都不给出 P1 结论**。取此名是因为它刻画的是受测运行时的*工程状态*（哪些契约条件当前守得住、哪些守不住），而非 P1 的科学状态。

### 9.2 威胁模型（2026-08-04 新增 §6.2）

论文此前通篇讲 authorization / mediation / gates，却从未声明谁被信任。新增 `sec:threat-model`，五条：

| 要素 | 立场 |
|---|---|
| trusted computing base | 控制面（compiler、registry、policy evaluator）被信任；其集中化风险在 §10.1 单列 |
| untrusted model output | plan 是**权限请求**，不是授权 |
| semi-trusted Skills | 声明可能与行为不符（引 `zhang2026misalignment`），typed closure 是闸门 |
| untrusted external content | 回答 prompt injection 的是**契约解析**，不是指令过滤 |
| adversary capabilities | 范围内：撰写/修改 Skill、影响请求文本、控制外部内容、组合危险路径。范围外：突破 Scaffold 隔离、伪造 attestation、颠覆控制面 |

收尾明确目标之窄：闸门与 trace 使违规**可归因**，但不阻止一个**已授权**的 effect 造成危害。

### 9.3 统计效力：交互项才是 P1 的落点（2026-08-04 新增 §9 preamble 段）

三条设计约束，写在协议前而非事后 caveat：

1. **margin 必须来自它所管辖的决策**（release board 可接受的最大语义退化、会改变采购/放置决定的最小容量响应偏离），**不得来自 pilot 观测方差** —— 否则噪声大的仪器可以靠放宽自己的 margin 自我认证。决策、决策 owner、数值 margin 分列为独立预登记字段。
2. **复现量按交互而非主效应定尺**：交互是差之差、累积每个参与 cell 的方差；只按 capability 轴与 capacity 轴两条主效应定功效的设计，会系统性无法解析 P1 真正依赖的 recoupling 项。须声明 runs/cell、最小可检出交互、以及它是否小于 interaction margin。
3. **功效不足须事先声明**：若最小可检出交互超过 margin，则该设计对 P1 功效不足，此时非显著交互对可分离性**不提供信息**、而非支持之。把"把功效不足报成独立性结论"点名为本研究纲领最可能产生自利假阳性的方式。

### 9.4 最省可行首个研究（2026-08-04 新增 §9.10）

对抗"证据要求重到无限期推迟一切证据"这一最大风险，给出能产出关于 P1 的可发表结果的最省配置：单租户、一个 workload family、单模型/tokenizer/policy 版本、**恰好两个** Scaffold class（不做拓扑扫描）、合成 Skill（声明面的 ground truth 可得，不必等生产 Skill 生态）、复现预算花在 runs/cell 而非更多 cell。

**不可削减的是 instrumentation**：六个条件全部工具化、六个违规率全部上报 —— 但**不要求全部通过**。instrument ≠ pass；一个 complete-mediation 率非零而其余五条为零的首个研究，给出的 conditional-engineering result 恰好点名真实运行时留着哪条通道、关闭它要多少钱，这比未上报的合取失败对下一个研究更有用。可接受的两处节省：diagnostic 注入减到 shared-compute + external-service quota 两条通道；语义不变性指标收窄到 task success + 每条需求全满足 + 五个 interface semantics。

预期产出明确而克制：六个违规率及其 instrumentation、跨两个 Scaffold class 的语义不变性区间、两点容量响应、带 achieved power 的交互估计、以及关闭每个被违反条件的成本账。这个规模**不能**建立可分离性，也不该声称能。它能建立的是"六个条件在运行系统中是否根本可工具化" —— 这一点目前未知，且是本节所有更大研究的前提。

### 9.5 无协议机制的如实登记（2026-08-04）

§7.3 的 mechanism 1（tool-set cohesion / prefix stability）、mechanism 4（seed-affinity placement）以及 Amdahl 标定 `s=s₀+λρ+ηz` / `E=E₀−μc̄` 在 §9 中**没有任何协议**：现行协议不把 ρ（tool-set overlap）与 c̄（handoff cost）作为受控因子扫描，而估计 λ/η/μ 恰需如此。正文现如实说明，并给出所需设计（固定 workload 与 Scaffold pool、以 overlap 与 handoff summary size 为操纵变量、线性形式本身对单调非线性备择受检）。Table 3 补两行：`Prefix stability / seed affinity`（Design pattern，No protocol in this paper）与 `Amdahl and handoff calibration`（Open question，No protocol in this paper）。

## 10. v22 聚焦修订快照（2026-08-04）

> 本节记录当前论文 v22；上文保留为 v20/v21 的历史设计与论证轨迹。v22 是 16 页、8 图的聚焦重写，不应把篇幅压缩误读为已经新增实证。

### 10.1 中心论点与责任边界

v22 将研究目标收敛为：**用显式、版本化、可测量的运行时契约，使 agentic runtime 的能力扩展与物理扩展在声明的 operating region `Ω` 内保持可管理，并允许该主张被证伪。**

| 对象 | v22 所有权 |
|---|---|
| **Skill** | 拥有版本化行为：目标、类型化输入/输出、可激活能力图及测试 |
| **Harness** | 拥有准入与逻辑控制：解析契约、选择激活图、授权 effects、绑定预算并生成 evidence |
| **Scaffold** | 拥有物理执行与隔离：资源、调度、故障域、locality、identity 与 attestation |
| **数据基盘** | 在运行时栈外治理语义数据与遥测数据；提供 policy、provenance 和版本事实，但不调度 agent |

Figure 2 中的解析契约统一写为五组字段：`I/O`（类型化输入与输出）、`G`（已激活 Skill 图）、`A`（authority、effects 与 evidence duties）、`B`（时间、成本、token 与并发预算）、`V`（policy、model、data、capability、verifier 与 trace 版本）。

### 10.2 有界可分离性与判决

v22 不主张全局独立。它只检验 `Ω` 内的 **bounded separability**：在能力干预和容量干预同时发生时，契约语义与资源响应是否仍落在预登记边界内。六项义务都必须以观测率报告，而不是用抽象布尔值替代：

1. typed closure；
2. complete mediation；
3. effect non-interference；
4. shared-state isolation；
5. resource invariance；
6. scheduler independence。

主实验采用 **cluster-period randomized crossover**：以集群-周期为随机化单元，在稳定窗口内交换基线与干预条件，控制时间趋势和集群差异。最终结论只能是 `supported`、`falsified` 或 `inconclusive`；功效不足、仪器缺失或 operating region 越界必须归为 `inconclusive`，不得写成支持性结果。

完整序列主估计不得掩盖 washout/reset 失败造成的处理后选择偏差。预登记必须按进入处理、退出处理、周期和顺序报告 reset-failure 与 sequence-completion rate，并配套覆盖全部随机化 cluster-period 的 assignment-based ITT 敏感性分析：reset failure 计为 `Q_req` 的运行失败，缺失 `R` 使用预登记最坏情形边界，并以 tipping-point 分析改变失败转移的潜在结果。若 reset failure 在处理间不平衡，或 P1 判决在敏感性范围内改变，则结论为 `inconclusive`。
