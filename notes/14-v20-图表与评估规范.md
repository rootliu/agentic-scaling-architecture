# v20 图表与评估规范

> **用途**：统一论文正文、Figure 8、表格、caption 和 builder 的词汇、责任边界与证据等级。图表必须帮助读者判断“谁拥有、谁不拥有、证据属于哪个平面”，而不是只展示分层外形。

## 1. 唯一术语表

| 对象 | 图中主标签 | 中文定义 | 不得暗示 |
|---|---|---|---|
| Skill | **Business capability: Skill-as-Code** | 可复用、版本化的业务能力与流程资产 | 不拥有运行时治理、执行资源或企业数据 |
| Harness | **Runtime governance: Harness** | 运行时编译器与治理器 | 不拥有业务语义、物理容量或数据本体 |
| Scaffold | **Execution and control boundary: Scaffold** | 执行与控制边界及 NFR 负责人 | 不解释业务语义，不决定数据口径 |
| 数据基盘 | **CIO-governed semantic and telemetry foundation: data substrate** | 栈外、由 CIO 独立治理的语义与遥测基础设施 | 不是第四运行时层，不调度 agent |

中文正文固定使用“Skill-as-Code”“运行时编译器与治理器”“执行与控制边界”“数据基盘”。“语义连接”用于 semantic join；不得把数据基盘画成 Scaffold 内部数据库。

## 2. 图面规范

四个英文标签在 builder 中由 `_draw_responsibility_band` 绘制，而该方法由公共 `draw()` 调用，因此**这条责任带出现在全部 8 张图的页脚位置，不是某一张图的专属内容**。它是全篇一致的责任词汇底座：

1. `Business capability: Skill-as-Code`
2. `Runtime governance: Harness`
3. `Execution and control boundary: Scaffold`
4. `CIO-governed semantic and telemetry foundation: data substrate`

前三者横排并以箭头相连，数据基盘作为栈外底带横跨全宽，与 Harness 之间以虚线箭头 + `governed-contract access` 标注相连。正文、caption 和 builder 常量必须与这四个字符串逐字一致。

### 2.1 承载责任交接的是 Figure 1，不是 Figure 8

两张图分工不同，规范不可互换：

| 图 | label | 内容 | 规范要点 |
|---|---|---|---|
| **Figure 1** | `fig:dual-scaling` | 企业责任与双扩展模型 | 责任交接关系 + 逻辑/物理两类干预的区分；caption 须说明数据基盘栈外、由 CIO 独立治理，且可分离性只在声明 operating region 内被检验 |
| **Figure 8** | `fig:evaluation-matrix` | 证伪矩阵 | 顶部四条契约关系文字 + 业务/系统双证据平面双栏 + 各命题的干预/观测/证伪条件行 |

Figure 8 顶部四条关系必须逐字为：

- `Skill -> Harness: versioned capability contract`
- `Harness -> Scaffold: admission + compatible capacity binding`
- `Harness <-> data substrate: semantic join + governed evidence`
- `Scaffold -> Harness: enforceable execution facts`

### 2.2 构图语法

- Skill、Harness、Scaffold 按责任交接关系排列，但不借几何位置暗示所有实现都必须三进程或三团队部署。
- 数据基盘用栈外基础设施表示，与 Harness 之间画受治理的语义、policy/provenance facts 和 telemetry 接口；不得画成 L4。
- **`0 到 100,000` 不出现在任何图内**（builder 全文无此字符串），因此"图中须紧邻标注 measurable design target"是一条无对象的规则。该限定的实际强制点在**正文**：§11 写成 "does not demonstrate operation from 0 to 100,000"，§12 写成 "is a measurable design target, not implementation evidence"。若将来把该数字画进图，才需同时加相邻限定语。

### 2.3 视觉编码

- 颜色只编码责任对象，不编码“成熟度”或“优劣”。
- 实线表示稳定契约，虚线表示 telemetry / evidence 回流；图例必须解释。
- 未经实证的路径不得使用“已验证”“proven”“production scale”等视觉徽标。
- caption 必须说明数据基盘栈外且由 CIO/数据权威独立治理，并说明所有权是责任模型而非强制组织图。

## 3. 必备表格

### 3.1 所有权、节奏与稳定契约表

| 对象 | 主要 owner | 变化节奏 | 稳定契约 |
|---|---|---|---|
| Skill | 业务产品 owner + AI/自动化开发者 | 小时到周 | 目标、类型化 I/O、effects、测试、证据、版本 |
| Harness | AI 平台/运行时/治理团队 | 天到月 | 准入、激活路径、effects、约束、后置条件、trace |
| Scaffold | 平台、云/服务器场、SRE、安全、运维 | 周到年 | 资源、隔离、locality、identity、attestation、执行 |
| 数据基盘 | CIO/数据权威 + 领域 data stewards | 周到年 | 语义访问、provenance、routing、lifecycle、中间表示 |

表注：一个团队可实现多个对象，但不可合并其决策权、稳定契约和证据责任。

### 3.2 责任边界与明确非所有权表

| 对象 | 业务语义 | 运行时治理 | 物理执行 | 企业数据 |
|---|---|---|---|---|
| Skill | owns | declares requirements | does not own | consumes governed contracts |
| Harness | compiles activated capability | owns | binds but does not supply | mediates access and evidence |
| Scaffold | does not interpret | exposes enforceable facts | owns | enforces locality/network boundary |
| 数据基盘 | preserves domain meaning | supplies policy/provenance facts | does not schedule | owns semantic integration/routing |

该表比较责任边界，不给具体产品打 completeness 分，也不声称现有产品缺少未公开能力。

### 3.3 双评估平面表

| 平面 | 核心问题 | measures | 证据 owner |
|---|---|---|---|
| 业务/use case | Skill 是否改善预期工作？ | success、需求全满足率、quality、cycle time、human correction、risk、unit economics | 业务 owner + 独立 evaluator |
| 系统/运行时 | 能否在企业规模下被可预测地准入和运营？ | contract validity、policy decisions、semantic invariance、throughput、tail latency、availability、isolation、replay、provenance、cost | Harness、Scaffold、安全、SRE、审计 |

表注：两个平面不可互相替代；self-correction 必须与 first-attempt grading 分列。

### 3.4 文献与证据资格表

每个进入论文的来源至少有以下列：

| Source ID | 准确发布日期 | 日期核验入口 | 证据平面 | 支持的有限结论 | 不支持的外推 |
|---|---|---|---|---|---|
| 示例：arXiv:2607.16345 | 2026-07-16；v2 2026-07-21 | arXiv API `<published>` / `<updated>` | 业务/use case | 首次评分与自修正须分列 | 不证明运行时可扩展 |

不得仅写年份，也不得以引用管理器导入时间、本地文件创建时间或二手文章日期代替发布日期。

### 3.5 Scaffold NFR 与规模表

| 责任域 | 指标 |
|---|---|
| 准入与容量 | admission throughput、active-agent capacity、queueing delay、saturation |
| 时延 | p50/p95/p99 latency |
| 稳定性 | failure/retry rates、control-plane availability |
| 安全 | isolation violations |
| 经济与依赖 | cost per completed run、external-service backpressure |

表头或表注必须把 `0 到 100,000 个 admitted/active agents` 标为可测设计目标，不得写成现有成绩。

## 4. 证据分类规则

### 4.1 先分证据平面

- **业务/use case 证据**：任务成功、需求完整、质量、周期、人类修正、业务风险、单位经济性。
- **系统/运行时证据**：契约、策略决定、准入、组合路径、吞吐、尾延迟、可用性、隔离、replay、provenance、成本。
- 同一研究可贡献两个平面的证据，但每项 measure 必须单独归类，不得用一项综合分数抹平边界。

### 4.2 再分主张等级

| 等级 | 可用措辞 | 必需证据 |
|---|---|---|
| 架构建议 | proposes / defines / assigns | 明确定义、边界、owner、反例与限制 |
| 机制假设 | is intended to / may enable | 可检验机制链、对照与证伪条件 |
| 实现证据 | implements / demonstrates in stated setup | 可审查 artifact、配置、workload 和测量 |
| 经验结果 | measured / observed | 数据、指标、基线、样本与不确定性 |
| 外部有效性 | generalizes within declared region | 多环境复现与预注册适用边界 |

架构图本身只能支持“定义”和“责任分配”，不能升级为实现证据或经验结果。

### 4.3 日期与来源资格

- **奠基性形式化文献（第二类例外）**：reference monitors/complete mediation（Anderson 1972、Saltzer & Schroeder 1975）、non-interference（Goguen & Meseguer 1982）、capability security（Miller et al. 2003）、information hiding（Parnas 1972）、policy-mechanism separation（Levin et al. 1975 Hydra）、control/data-plane separation（Kreutz et al. 2015）、MAPE-K（Kephart & Chess 2003 / IBM 2006）、ISO/IEC 25010、queueing 与干扰（Kleinrock 1975 / Mars & Tang 2011 / Dean & Barroso 2013）——作为学术谱系锚点，不受 2026-06-01 当代规则约束。v23 已在企业白皮书 references.bib 补入 13 条并建 `Classical foundations` 映射段。
- Conway 1968 是第二类历史例外，只用于组织沟通的历史背景。
- 所有当代来源必须核验准确发布日期，且不早于 `2026-06-01`。
- 当代 arXiv 来源优先核对官方 API 的 `<published>` 与 `<updated>`；行业来源核对官方发布页可见日期及页面 metadata。
- 无法核验准确日期的当代资料不进入论文证据表；只写“2026”不合格。
- 早于当代边界但构成设计动机的来源（如 Policy-Driven Runtime Layer 2605.27744、Tool Forge 2605.28000、SkillOpt 2605.23904）按 SkillOpt 模式在正文登记为设计动机、非证据引用、不断言其结果。
- 文献只能支持其测量范围内的有限结论，不得用单个实现推出 Testable Separability Conjecture、普遍安全或企业级规模已经成立。

### 5.4 交叉引用完整性（2026-08-04 新增）

正文一律用 `\ref` + `\label`，**不写死数字**。任一节或图表插入都会使硬编码数字集体失效，而这类失效不报错、只静默出错。

- [ ] 每个被正文引用的 section / figure / table / protocol 都有 `\label`；命名前缀固定为 `sec:` / `fig:` / `tab:` / `prop:`。
- [ ] 正文无残留硬编码引用：扫 `Figure [0-9]`、`Section~?[0-9]`、`Protocol[s]? [0-9]`、`\S[0-9]` 应为零命中。
- [ ] 构建器 `reference_label_map()` 与 `main.tex` 的 label 集合一致；渲染后扫 PDF 无 `the section` / `the protocol` / `the table` / `the figure` 降级回退（散文中合法出现的需逐一确认）。
- [ ] 范围引用用 `\S\ref{a}--\ref{b}` 而非 `\S\ref{a}--\S\ref{b}`（后者渲染成 `Section 9.1-Section 9.2`）。
- [ ] `prop:` label 不进 `reference_label_map`，它们渲染为 `P1` 而非编号。

## 6. 禁止主张与归因

以下表达不得进入 v20 正文、图、表或 caption：

- “系统已支持/验证 0 到 100,000 agents”，除非未来有对应 artifact 和完整指标；当前只能写设计目标。
- “Skill-as-Code 保证确定性、安全、组合正确、业务价值或可移植性。”
- “Harness 已证明逻辑扩展与物理扩展独立/正交”；只能写待证伪的有界 conjecture。
- “语义连接已经解决企业异构数据集成”或“数据基盘是第四运行时层”。
- 用业务/use case benchmark 证明系统/运行时 deployability，或反向用运行时可靠性证明业务价值。
- 把“企业 IT 架构就是企业沟通协议”归因给 Conway 或任何外部作者。
- 除 Conway 1968 外，引用发布日期早于 2026-06-01 或只有年份、无法核验准确日期的当代资料。
- 对具体框架、云服务或产品做无证据的 completeness 排名，或声称其缺少未公开能力。
- 把 proposal、机制假设、有限实现或单环境测量写成普遍经验事实。

## 7. v22 图表与评估补充（2026-08-04）

> 上文是 v20 图表规范的历史基线；本节是当前 16 页、8 图 v22 的增量约束。

### 7.1 八图叙事顺序

八张图必须形成从论点到验证的连续链条，并各自带有能独立阅读的说明：先给出研究对象与责任交接，再解释契约编译、数据基盘、生命周期与物理执行，最后落到可证伪的实验设计和判决矩阵。caption 至少回答“图中对象是什么、箭头表示什么、该图不证明什么”。

Figure 2 的契约字段只能使用以下规范标签：

| 字段 | 图内说明 |
|---|---|
| `I/O` | typed inputs and outputs |
| `G` | activated Skill graph |
| `A` | authority, effects + evidence duties |
| `B` | time, cost, token, concurrency budgets |
| `V` | policy, model, data, capability, verifier + trace versions |

长字段必须换行或扩大单元格，不得溢出边框；同一字段在正文、图注和测试中须逐字一致。所有缩写首次出现时在正文或 caption 展开，图内可保留短标签。

### 7.2 v22 评估读取规则

- 六项义务分别报告观测率与阈值：typed closure、complete mediation、effect non-interference、shared-state isolation、resource invariance、scheduler independence。
- 主设计写全为 **cluster-period randomized crossover**，并说明集群、周期、随机化与 washout/stability window 的定义。
- operating region `Ω`、干预、estimand、margin、最小可检出交互和 achieved power 必须随结果一起报告。
- complete-sequence 主估计必须同时报告按进入/退出处理、周期和顺序分层的 reset-failure 与 sequence-completion rate，并给出 assignment-based ITT 边界及 tipping-point 敏感性分析；处理间失败不平衡或判决随敏感性假设改变时归为 `inconclusive`。
- 论文级判决只允许 `supported / falsified / inconclusive`。缺数据、缺仪器、功效不足或越界一律为 `inconclusive`。
- 架构图仍只支持定义和责任分配；八图齐全不构成实现或经验结果。
